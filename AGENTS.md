# Knock Knock Agent Guide

This is the internal engineering and product reference for Knock Knock. Keep
`README.md` customer-facing: what the app is, how to run it, and where the
main pieces live. Put product choices, technical tradeoffs, release caveats,
API contracts, and agent-specific runbooks here.

## Product Direction

Knock Knock is a phone-number-only dating app built around one event a day.
Every night from **7:00 to 8:00 PM America/Los_Angeles**, the doors open and
you get **5-minute video speed dates**, one after another, with people
within **75 miles** who match your preferences. After each date both people
privately choose **keep talking** or **pass**; a mutual yes unlocks a
**text-only chat** (no images, no attachments). Everything is keyed on phone
number. There's no browsing, no swiping through photos, no profile feed:
you show up, talk to someone on video, and decide after actually talking to
them.

The product used to be a knock-rhythm video caller for people who already
know each other (contacts, recents, group calls, CallKit-based ringing).
That's gone. CallKit and PushKit are removed entirely (App Review rejected
1.0.2 over CallKit plus China availability), so there's no VoIP background
mode and no CallKit symbols anywhere in the binary.

Current v1 scope:

- Native iOS client only.
- Phone OTP auth (Firebase phone verification or backend-issued OTP,
  depending on `SMS_PROVIDER`).
- Profile setup: name, birthday, gender, who you want to see, age range,
  bio, optional photo, location.
- Nightly lobby, matcher, 5-minute 1:1 video dates over LiveKit.
- Mutual-yes matching and text-only chat.
- Block and report.

Non-goals for v1:

- Per-user timezones (the window is 7–8 PM Pacific for everyone, for now).
- User-adjustable match radius (fixed at 75 miles).
- Photos or attachments in chat.
- Android (frozen on the old calling product, see below).

## Technical Shape

- iOS: SwiftUI, XcodeGen project in `ios/project.yml`, bundle id
  `app.exla.slide`, scheme `Slide`.
- Android: Kotlin/Compose, Gradle Kotlin DSL, Play application id
  `app.slide`. **Frozen on the old "Knock Knock - Video Chat" calling
  product.** It has not been migrated to speed dating; do not assume its
  code or store listing reflect anything in this document. It gets its own
  pivot later.
- Web: Next.js marketing site in `web/`, deployed to Vercel at
  `https://slide.viraat.dev`.
- Backend: Rust `axum` API (`crates/slide-api`), `sqlx`, Postgres, Redis.
- Media: LiveKit, one room per date, joined with a short-lived per-user JWT.
  `crates/slide-sfu` (the old webrtc-rs SFU) is legacy: it stays in the
  workspace so it keeps compiling, but no maintained client uses it.
- Shared core: `crates/slide-core` for models, JWT, OTP, and phone E.164.

## Design System

The identity is warm and quiet: eggshell backgrounds, espresso-brown type, a
terracotta accent for warmth and destructive actions, hairlines instead of
shadows. Keep the system consistent across iOS and web. Tokens live in
`ios/Sources/DesignSystem/Theme.swift`; this table mirrors them.

Color tokens:

- `bg`: `#FAF6EF`, warm eggshell, every background.
- `bgGrouped`: `#F2ECE1`, slightly deeper eggshell for grouped sections.
- `text`: `#2A211B`, warm dark-brown primary text.
- `textSecondary`: `#8A7C6D`, warm taupe secondary text.
- `hairline`: `#E6DCCB`, 1px borders and dividers.
- `accent`: `#5A4632`, rich espresso brown, primary action and active
  toggles.
- `danger` / `warm`: `#D4694F`, terracotta. Used for destructive actions
  (leave date, log out, delete account) and for warm urgency (countdown
  ring in the last minute) without reading as an error.
- `onAccent`: `#FAF6EF`, cream text/icon on filled brown buttons.
- Chat bubbles: mine = `accent` fill with cream text; theirs = `bgGrouped`
  fill with a hairline stroke.

Typography:

- System font: SF Pro on iOS, `-apple-system`/Inter on web.
- Weights: Light 300 for large headings, Regular 400 for body, Medium 500
  only for buttons and active states.
- Small uppercase labels use tracking around `0.02em`.
- The "Knock Knock" wordmark is thin, around 300 weight, tracking `0.04em`.

Shape, spacing, and motion:

- 8px spacing grid. Touch targets at least 44px.
- Corner radius 14–22px, soft and rounded.
- Prefer 1px hairlines over cards with shadows.
- Motion is fast and subtle, 150–200ms ease-out.
- The lobby's "finding someone" pulse is gentle, scale 1.0 to 1.04.
- Icons are thin line icons, about 1.5px stroke.
- Bottom navigation has three tabs: Tonight, Matches, Profile.
- The date screen and any full-screen flow (lobby, decision, match) take
  over above the tabs.

## API Contract

Base URL is `/v1`. All JSON uses camelCase. Auth uses
`Authorization: Bearer <accessToken>` except auth endpoints. Errors use:

```json
{ "error": { "code": "rate_limited", "message": "too many requests", "retryAfter": 30 } }
```

### Auth

| Method | Path | Body | Returns |
|---|---|---|---|
| POST | `/auth/request-otp` | `{ "phone": "+14155550123" }` | `{ "status": "sent", "transport": "review"\|"sms"\|"firebase" }` |
| POST | `/auth/verify-otp` | `{ "phone", "code" }` | `{ "accessToken", "refreshToken", "isNewUser", "user": MeView }` (same shape as `GET /me`) |
| POST | `/auth/firebase` | Firebase phone-auth ID token | `{ "accessToken", "refreshToken", "isNewUser", "user": MeView }` |
| POST | `/auth/refresh` | `{ "refreshToken" }` | `{ "accessToken", "refreshToken" }` |
| POST | `/auth/logout` | `{ "refreshToken" }` | `204` |

`transport` tells the client what actually happened, so it never sits on a
code screen waiting for an SMS that doesn't exist:

- `review`: the phone is in `REVIEW_PHONES` and `REVIEW_OTP_CODE` is set. No
  SMS is sent; the client submits the fixed review code.
- `sms`: `SMS_PROVIDER` is a real provider (sns/twilio); the backend sends
  the code itself. With `EXPOSE_DEV_OTP=true` (local/CI only) the response
  also carries `devCode` so scripts don't have to read SMS.
- `firebase`: `SMS_PROVIDER=console` (production today). The backend sends
  nothing and stores no challenge; the iOS client must run Firebase phone
  verification itself and exchange the resulting ID token at
  `POST /auth/firebase`.

### Diagnostics

| Method | Path | Body | Returns |
|---|---|---|---|
| POST | `/diagnostics` | `{ "event", "detail"?, "phoneCountry", "os", "device", "app"? }` | `204` |

Unauthenticated, for client-side failures that never reach a human (a
reviewer's device, a user who closes the app on an error). `event` is
1-64 chars of `[a-z0-9_]`; `detail` and `app` are optional (`detail` up to
500 chars, `app` up to 64); `phoneCountry`, `os`, and `device` are required,
each up to 64 chars. Anything else is `422`. Rate-limited 20/min per client
IP (from `Fly-Client-IP`/`X-Forwarded-For`, falling back to the TCP peer).
The body is never stored: on success the backend emits one structured
`tracing` line (`warn` when `event` ends in `_failed`, `info` otherwise) so
it shows up in `fly logs`, then returns `204`.

### Session

| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/session` | none (auth) | `SessionWindow` |

```json
{ "isOpen": true, "opensAt": "2026-09-12T02:00:00Z", "closesAt": "2026-09-12T03:00:00Z",
  "sessionDate": "2026-09-11", "serverTime": "...", "timezone": "America/Los_Angeles",
  "dateSeconds": 300, "radiusMiles": 75 }
```

`session.rs` is the only place that computes the window: doors are open
`[SESSION_OPEN_HOUR:SESSION_OPEN_MINUTE, SESSION_CLOSE_HOUR:SESSION_CLOSE_MINUTE)`
in `SESSION_TZ`, every day, for everyone (per-user timezone is a known
follow-up, see below). Review accounts and `SESSION_ALWAYS_OPEN=true` always
see the session as open, with `closesAt` an hour out.

### Profile

| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/me` | none | `MeView` |
| PATCH | `/me` | `{ "displayName"?, "birthdate"?, "gender"?, "interestedIn"?, "ageMin"?, "ageMax"?, "bio"? }` | `MeView` |
| PUT | `/me/photo` | raw `image/jpeg` (or multipart field `file`), ≤ 600 KB | `{ "photoUrl", "photoUpdatedAt" }` |
| DELETE | `/me/photo` | none | `204` |
| GET | `/users/:id/photo` | none (auth) | `image/jpeg`, `Cache-Control: private, max-age=300`; 403 if either side has blocked the other; otherwise served only to the user themselves or to a partner with an active match (`unmatched_at IS NULL`), every other case is 404 (no photo, no match, unmatched) so the call never confirms a photo exists for an id the caller only knows from an anonymous date |
| PUT | `/me/location` | `{ "lat", "lng" }` | `204` |
| DELETE | `/me` | none | `204`, deletes the account (FK cascades), revokes refresh tokens, removes push subscriptions |
| POST | `/push/register` | `{ "pushToken", "kind": "apns", ... }` | `{ "ok": true }` (only `apns` is accepted; other kinds get `422`) |
| DELETE | `/push/register` | `{ "pushToken" }` | `204` |
| POST | `/devices` | `{ "pushToken", "platform", "appVersion" }` | `Device` (kept for client compatibility) |

```json
MeView {
  "id", "phone", "displayName": "Maya", "birthdate": "1996-04-02", "age": 30,
  "gender": "woman", "interestedIn": ["man", "nonbinary"], "ageMin": 25, "ageMax": 38,
  "bio": "...", "hasPhoto": true, "photoUrl": "/v1/users/<id>/photo", "photoUpdatedAt": "...",
  "profileComplete": true, "hasLocation": true, "isReviewAccount": false,
  "createdAt": "...", "lastSeenAt": "..."
}
```

Validation: `displayName` 1–40 chars trimmed; `birthdate` implies age ≥ 18
and ≤ 100 (computed in `SESSION_TZ`); `gender` one of `woman`/`man`/
`nonbinary`; `interestedIn` a non-empty deduped subset of those three;
`18 ≤ ageMin ≤ ageMax ≤ 99`; `bio` ≤ 300 chars. `profileComplete` is derived
from `displayName`/`birthdate`/`gender`/`interestedIn` all being present.
Location is stored rounded to 2 decimals (about 1 km, "coarse" for the
privacy label).

### Lobby and matching

| Method | Path | Body | Returns |
|---|---|---|---|
| POST | `/lobby/join` | none | `{ "status": "waiting" }` or `{ "status": "matched", "date": DateSession }` |
| POST | `/lobby/heartbeat` | none | same shape as `/lobby/join`; call every 5 s |
| DELETE | `/lobby` | none | `204` |
| GET | `/dates/current` | none | `{ "date": DateSession \| null }` |
| GET | `/dates/today` | none | `[{ "id", "partner": PublicProfile (redacted unless `matched`), "startedAt", "endedAt", "myDecision": true\|false\|null, "matched": bool }]`; `matched` means an active match (`unmatched_at IS NULL`, same rule as `GET /matches`), so an unmatched or blocked pair goes back to `matched: false` with the redacted card |
| POST | `/dates/:id/leave` | none | `204`; ends the date (`end_reason='left'`), publishes `date_ended` to both |
| POST | `/dates/:id/decision` | `{ "explore": true }` | `{ "status": "waiting"\|"matched"\|"passed", "match": MatchSummary? }` |

`/lobby/join` fails with `409 session_closed`, `422 profile_incomplete`,
`422 location_required`, or `409 date_in_progress` (with the open `date`)
when a precondition isn't met. `/lobby/heartbeat` doubles as the poll
fallback for a missed `date_matched` WebSocket event: if the caller already
has an open date, it comes back as `matched`.

Decisions are answered once: replaying the same answer returns the current
status, changing it is `409`. A `false` from either side is never revealed
to the other, they just stay `waiting`. Both `true` creates the match,
publishes `match_made` to both, and sends an APNs alert to whichever side
answered first.

```json
DateSession {
  "id", "roomId", "sfuUrl", "joinToken", "startedAt", "endsAt", "dateSeconds": 300,
  "partner": PublicProfile   // redacted, see below
}
PublicProfile { "id", "displayName", "age", "gender", "bio", "hasPhoto", "photoUrl", "distanceMiles": 12 }
```

Dates are anonymous. `DateSession.partner` keeps the `PublicProfile` shape
so the 1.1.0 client decodes it, but it is redacted (`views.rs`,
`PublicProfile::redacted`): `id` is the partner's user id, `displayName` is
the placeholder `"your date"` (the 1.1.0 decision screen reads "Keep
talking with \(name)?" and has no fallback for an empty name), and every
other field is empty (`age: null`, `gender: null`, `bio: ""`,
`hasPhoto: false`, `photoUrl: null`, `distanceMiles: null`). `gender` must
be `null`, never `""`: the shipped client decodes it as an optional enum,
and an empty string fails decoding for the whole `DateSession`. The client
uses the id only for block/report and mock video. The real card is first
handed out inside the `MatchSummary` that a mutual yes produces
(`/dates/:id/decision`, `match_made`, `/matches`); `GET /dates/today`
returns the redacted card for every row except a `matched` one, whose
partner is already revealed. `age` is `null` on a redacted card and,
defensively, for a target with no birthdate.

`joinToken` is a LiveKit JWT minted per-recipient (identity = your user id,
no `name` claim so room metadata carries no display name, room = the date
id, ttl = `DATE_SECONDS + 120`); if LiveKit isn't configured the endpoint
returns `503 unavailable`. `distanceMiles` is haversine over the two stored
coarse locations, rounded to an integer, and `null` if either side has
none.

The matcher (`matcher.rs`) runs every 1.5 s plus once synchronously at the
end of `/lobby/join`: it drops stale lobby rows (no heartbeat in 20 s), then
greedily pairs waiting users in join order on mutual gender preference,
mutual age range, distance within `MATCH_RADIUS_MILES`, no block either
way, no date already tonight, and no active match. Two review accounts
skip preference/age/distance/"dated already" checks and always pair with
each other. A separate expirer closes dates past `endsAt` every second,
publishing `date_ended { "reason": "timeout" }`.

### Matches and chat

| Method | Path | Body | Returns |
|---|---|---|---|
| GET | `/matches` | none | `[MatchSummary]`, ordered by last activity, excludes unmatched/blocked pairs |
| GET | `/matches/:id/messages?before=<id>&limit=50` | none | `{ "messages": [Message, ascending], "hasMore": bool }` |
| POST | `/matches/:id/messages` | `{ "body": "..." }` | `201 Message` |
| POST | `/matches/:id/read` | none | `204` |
| DELETE | `/matches/:id` | none | `204`; publishes `match_removed` to the partner |

```json
MatchSummary { "id", "partner": PublicProfile, "createdAt", "lastMessage": { "id", "senderId", "body", "createdAt" } | null, "unreadCount": 3 }
Message { "id", "matchId", "senderId", "body", "createdAt" }
```

Message body: trimmed, 1–2000 chars, no control characters other than
newline/tab, rate-limited to 30/min per user. Sending publishes `message`
to both users (including the sender's other devices) and, if the recipient
has no live socket, an APNs alert. `unreadCount` counts partner messages
since `match_reads.last_read_at` (or all of them if never read). Every
`/matches/:id/*` route 404s for anyone but the two people in the match, and
paging is `before`-based backwards from the newest message (see "Known
follow-ups" for a gap here).

### Safety

| Method | Path | Body | Returns |
|---|---|---|---|
| POST | `/users/:id/block` | none | `204` |
| DELETE | `/users/:id/block` | none | `204` |
| POST | `/users/:id/report` | `{ "reason", "details"?, "dateId"?, "matchId"? }` | `204` |

Blocking unmatches any active match (`match_removed` to the other side) and
ends any open date between them (`end_reason='blocked'`, but the other side
only ever sees `date_ended` with reason `"left"`, a block is never
revealed). `reason` on a report is one of `inappropriate`/`harassment`/
`fake`/`underage`/`other`; `details` ≤ 1000 chars.

### Realtime

`GET /v1/ws?token=<accessToken>`, same auth as before, client sends
`heartbeat` every 25 s, server times out at 90 s, `connected {}` on open.

Server to client events, all JSON objects with `"type"`:

- `date_matched { "date": DateSession }`
- `date_ended { "dateId", "reason": "timeout" | "left" }`
- `match_made { "match": MatchSummary }`
- `match_removed { "matchId" }`
- `message { "matchId", "message": Message }`
- `connected {}`

There is no knock-rhythm event anymore; the old `knock`, `incoming_call`,
`call_accepted`/`declined`/`ended`, and `participant_joined`/`left` events
are gone along with the calling product.

### Review accounts

App Review has to be able to test outside 7–8 PM Pacific, on one device,
without a second reviewer. `review.rs` handles this for any phone in
`REVIEW_PHONES` (comma-separated E.164) when `REVIEW_OTP_CODE` is set:

- The account is flagged `is_review_account=true` and, if its profile is
  incomplete, gets one filled in automatically (name, birthday, gender,
  broad preferences, a seeded bio and location).
- A standing demo account (`REVIEW_DEMO_PHONE`) always exists, profile
  complete.
- The first `REVIEW_PHONES` entry gets an active match with the demo
  account plus three seeded chat messages, so chat/report/block/unmatch can
  all be exercised on one device without waiting for a live date.
- Review accounts always see the session as open, and two review accounts
  in the lobby pair with each other regardless of preferences or distance.

Current fixed values: review phones `+16505550100` (has the seeded match)
and `+16505550101`, review OTP = the `REVIEW_OTP_CODE` Fly secret (never committed; the value is in ASC review notes), demo phone `+16505550199`. These
live in `.env` locally and as Fly secrets in production.

## iOS Identity and Permissions

- `MARKETING_VERSION`/`CURRENT_PROJECT_VERSION` are set in `ios/project.yml`.
  Bundle id `app.exla.slide`; scheme/target name `Slide` (fastlane depends
  on it) even though the shipped name and home-screen label are "Knock
  Knock."
- `UIBackgroundModes` is `audio` only, so a date keeps its audio if the
  phone locks. There is no `voip` mode, no CallKit, no PushKit, no
  `CXProvider`, no `PKPushRegistry` anywhere in the app. Entitlements keep
  `aps-environment` for ordinary alert pushes.
- Usage strings are plain: camera and microphone explain they're for video
  dates, location explains the 75-mile radius and that it's stored rounded
  to about a kilometer. There is no contacts usage string; contacts access
  is gone from the app entirely.
- Firebase phone auth is the SMS transport (needs
  `ios/Resources/GoogleService-Info.plist`, gitignored, present locally and
  restored from a secret in CI). The backend OTP path is used when the
  server reports `transport: "sms"` or `"review"`.

## Sounds

All bundled `.caf` files under `ios/Resources/` are synthesized (no
licensed audio), generated by `ios/tools/make_sounds.py`:

- `knockknock.caf`: two warm wooden knocks, the 5-minute mark ending a date.
- `knock.caf`: single knock, the 7 PM doors-open push and the welcome
  gesture.
- `match.caf`: warm rising three-note marimba, a mutual match.
- `found.caf`: two quick rising notes, a partner found / date starting.
- `ended.caf`: two soft descending notes, a date ending after the knocks.
- `tick.caf`: a very short soft tick, the last 10 seconds of a date.
- `message.caf` / `message_received.caf`: soft pops on chat send/receive.

## Deployment Status

Current known live surfaces:

- Landing site: live at `https://slide.viraat.dev`, Vercel project `web`,
  including `/privacy` and `/terms`. The project is not git-connected to
  this repo, so a push does not deploy it; ship with `cd web && npx vercel
  --prod` (the folder is linked through the gitignored `web/.vercel`).
- Backend API: live on Fly at `https://slide-api.fly.dev`, Fly app
  `slide-api`, org `exla`.
- API health: `GET /v1/health` returns `ok`.
- Backend deploy command: `fly deploy -c deploy/fly/slide-api.fly.toml`.
- Backend image: built from `deploy/aws/Dockerfile.allinone` on each Fly
  deploy.
- Backend caveat: Fly runs a single API machine because app signaling and
  the lobby hub are in-memory. Keep `min_machines_running = 1` and don't
  scale horizontally until that state is durable/shared.
- Media: LiveKit, one deployment shared by all dates; `LIVEKIT_URL`,
  `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET` must all point at it or date
  endpoints return `503`.
- iOS: App Store Connect record `Knock Knock - Video Chat` (Apple ID
  `1780017294`) is renamed to `Knock Knock - 5 Minute Dates` at release
  time for 1.1.0.
- Android: debug APK builds against the old calling product only; not part
  of this pivot.

Production backend guidance:

- `DATABASE_URL` is a Fly secret pointing at managed Postgres. Redis is
  bundled in the all-in-one container unless a `REDIS_URL` secret is set.
- `sqlx` uses prepared statements, so use a direct Postgres connection or a
  session pooler on port 5432, not a transaction pooler on 6543.
- `SMS_PROVIDER=console` is dev/demo only; production runs the Firebase
  phone-auth transport instead (see the API contract's `transport` field)
  or a real SMS provider.
- Unknown environment variables must be ignored at boot, never fatal, since
  Fly still carries a few legacy secrets from the calling product.
- Push goes to APNs over HTTP/2. The workspace `reqwest` in `Cargo.toml`
  must keep the `http2` feature; without it every send fails with "error
  sending request" while `/v1/health` stays green. The nightly job logs
  `scheduler: doors-open push sent=N failed=M pruned=P recipients=K` right
  after 7:00 PM Pacific (`SESSION_OPEN_HOUR` defaults to 19); `sent=0` with
  recipients means APNs is broken, not that nobody is signed up.
- To test-fire a real push with the production secrets, run the binary on
  the Fly machine in its one-shot mode:
  `fly ssh console -a slide-api -C "/usr/local/bin/slide-api push-test --phone +14155550137"`
  (or `--user <uuid>`). It loads the same env, connects to Postgres, sends
  "Test: notifications are working." to every APNs token the account has,
  prints one line per token with Apple's status or error (tokens masked to 8
  chars, and transport errors printed without the request URL so a full
  token never lands in the output or the logs), and exits 1 unless at least
  one token was accepted and none were rejected. It refuses to send unless
  `APNS_ENV` is exactly `sandbox` or `prod`, the same guard `serve()`
  applies at boot. A 200 from Apple means the push was accepted; the device
  still has to allow notifications for Knock Knock in Settings, so a clean
  run with nothing on the phone points at the device's notification
  permission, not at APNs. It never starts the server or the scheduler.

```bash
APPLE_TEAM_ID=XXXXXXXXXX

```

**Known local build issue:** on this Mac, Xcode 26.6's build service
deadlocks during `CreateBuildDescription`: `SWBBuildService` runs a
`clang -v -E -dM` capability probe into a 16 KB pipe it never drains, the
iOS SDK's macro dump overflows it, and `clang` blocks in `write()` forever.
`xcodebuild`/`fastlane gym` never return. The fix is to hand both compilers
a wrapper that answers the `-dM` probe directly and execs straight through
to the real `clang` for every other invocation:

```bash
xcodebuild ... CC=ios/tools/clang-probe-wrapper.sh CPLUSPLUS=ios/tools/clang-probe-wrapper++.sh
```

Pass both env vars on any `xcodebuild archive`/`build` or `fastlane gym`
call on this machine. `ios/tools/clang-probe-wrapper.sh` and its `++`
sibling are checked in; they're transparent everywhere else, so it's safe
to pass them by default.

The CI alternative avoids the whole problem by archiving on a clean macOS
runner: `.github/workflows/ios-release.yml` (workflow_dispatch, or
`gh workflow run ios-release.yml -f build_number=33`) restores the signing
identity and API key from repo secrets, archives, verifies no
CallKit/PushKit symbols made it into the binary, and uploads the `.ipa` to
App Store Connect. It's driven entirely by these repo secrets:

| Secret | Contents |
|---|---|
| `IOS_DIST_P12_B64` | Apple Distribution identity, base64-encoded `.p12` |

## Secret Handling

Never commit:

- `.env` or `.env.*` except `.env.example`.
- App Store `.p8`, `.pem`, `.p12`, or `ios/fastlane/.asc.env`.
- Android keystores, `android/keystore.properties`, or Play service-account
  JSON.
- `ios/Resources/GoogleService-Info.plist` (Firebase client config,
  gitignored; restored from a secret in CI).
- Real phone numbers, videos, OTPs, live API tokens, or production
  credentials in docs, screenshots, tests, or issue comments.

Use obviously fake examples such as `+1 415 555 0137` and `a@example.com`.
Where a secret lives (which files, which GitHub Actions secrets) is tracked
in `SECURITY.md`; keep that table current when a new credential shows up.

## Known follow-ups

- **Per-user timezones.** The session window is 7–8 PM
  `America/Los_Angeles` for every account, everywhere. `session.rs` is
  written as the one place that would change if this becomes per-user.
- **Android rewrite.** The Android app is still the old knock-rhythm
  calling product and has not been touched for this pivot. It needs its own
  rewrite against the API contract above before it can ship speed dating.
- **Chat pagination polish.** `GET /matches/:id/messages` pages backwards
  with `before`, but the client-side scroll-position handling while paging
  older messages during an active conversation could use more testing
  under real network conditions.
- **App Privacy labels are web-UI only.** Apple's App Privacy questionnaire
  in App Store Connect has no API; `store/privacy.md` documents the answers
  to enter, but someone has to click through the actual form by hand for
  every submission that changes what data is collected.
